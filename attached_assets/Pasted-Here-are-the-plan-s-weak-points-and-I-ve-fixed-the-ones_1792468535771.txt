Here are the plan's weak points, and I've fixed the ones I could. The plan as it stands would likely produce green offline tests and still not run live. I also read the admission code myself instead of leaving it to Replit.

## Where the plan was weak
1. **"Working" was never defined.** Replit could pass 40 offline checks and call the project done. I've added an acceptance test below.
2. **Admission was left for later, and it's the real blocker.** I found the likely route. `pilot.ts` has a SINGLE stage that needs no earlier proof. In `discovery-scheduler.ts`, a job with a permit skips the global denial check (`collectionBlock`). The run guard only rejects UNCERTAIN and RESTART states. A successful verified pilot then clears the denial itself (`pilot.ts:~425`). So the path is the existing prepare, approve and run commands for one SINGLE pilot with `recordCap` 1. Replit must confirm or refute this with file and line, not assume it.
3. **A trap in that path.** Pilot scope requires the start date to be today or later, Eastern time (`pilot.ts` run guard). Only a fresh calendar for a future or current day can be used.
4. **The research-proof stage is a dead end.** It uses hard-coded docket URLs with no `dnh` token (`research-scope.ts`). That explains the 2026-10-18 MDJ 401, and it breaks the rule against building URLs. It must not be used.
5. **The enum gap can wreck the first live run.** If the first docket has conditional bail, the code produces `RECORDED_BAIL_AMOUNT`. The development database may reject it, the pilot would fail verification, and we'd have wasted the single run. The dev migration must be applied before any live step.
6. **The plan ignored the shipped limits, which make the 200-docket goal impossible by default.** Defaults are 5 documents per job (`UJS_MAX_RECORDS`), 30 requests per hour and 120 per day. Raising them is your decision, not a patch. Given the 429 at 44 dockets on October 5, I would stay at 1, then 5, and decide after that.
7. **Verification can fail even when the PDF succeeds.** The pilot requires every request under 20 seconds and no latency warning. The slow, paced calendar assets could fail that. The result would be a working PDF with the stop still set. Replit must report which condition failed.
8. **The planned tests would miss a real defect.** Real links carry `dnh` values with `%2B`, `%2F` and `%3D`. No planned test proves the downloader sends those bytes unchanged. I've added one.
9. **Nothing independent checks the output.** The app would certify itself. I've added a human check against the portal.
10. **The Playwright calendar is the fragile part.** If it fails inside the pilot, don't retry. The fallback is a plain-HTTP calendar (it returned 1,002 links twice for me), written as v17. I'd spec that only if needed.

## Acceptance test for "working"
- **A1.** A fresh calendar search for a current or future date validates at least 1 row.
- **A2.** The app itself fetches one docket PDF with the plain-HTTP method, within a recorded number of seconds of link capture.
- **A3.** The PDF has the `%PDF-` signature, the docket number matches, and the SHA-256 is stored.
- **A4.** The bail row is extracted with page and quoted text, or correctly reported as nonmonetary or ambiguous.
- **A5.** The row shows on screen and in CSV with the required disclaimer, and the two match.
- **A6.** You open the same docket on the portal and confirm the extracted row matches the bail section.
- **A7.** The request ledger shows exactly the expected requests, no retries, and the denial cleared by the approve step, with an audit event.
