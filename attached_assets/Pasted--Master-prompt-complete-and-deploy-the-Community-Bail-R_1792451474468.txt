# Master prompt: complete and deploy the Community Bail Research Tool

## Objective

Finish the existing application so a signed-in user can enter court-calendar criteria, run a search, and receive verified docket-backed monetary bail observations.

The completed workflow is:

```text
Calendar criteria
→ validated court search results
→ associated docket PDFs
→ verified event and bail extraction
→ qualifying results
→ expandable evidence
→ CSV export
```

The main results table contains exactly:

| Hearing date | Docket number | Bail amount |
|---|---|---|

Posted monetary bail qualifies. No explicit qualifying monetary bail amount means no row in the main table.

Your job is to deliver a **functioning deployed app**, not a plan, mockup, parser-only demonstration, or collection of disconnected components.

## 4. Monetary inclusion and interpretation

### Include

Include an unambiguous explicit monetary bail-setting observation associated with a matching calendar event.

Posted bail qualifies.

Historical monetary setting observations may qualify. Their inclusion does not mean they remain operative.

### Exclude from the main table

- Missing monetary bail amount.
- Nonmonetary, recognizance, unsecured, nominal, or denied entries outside the monetary-setting scope.
- Unreadable documents.
- Wrong docket identity.
- Unsupported or ambiguous amount association.
- Missing or unresolved matching-event date.
- Amounts outside the selected monetary filter.

Show exclusions and failures in the job outcome report.

### Extract the recorded amount

Use the bail entry’s recorded Amount field.

Keep separate:

- Percentage.
- Posted-security amount.
- Fines, fees, costs, restitution, and other dollar figures.

Do not calculate a replacement amount from the percentage.

Do not substitute posted security for bail.

Use integer cents internally and two-decimal currency formatting in the interface.

If the current financial-basis model cannot accurately represent a verified recorded amount, make the smallest compatible additive change. Do not force it into `TOTAL_BAIL` merely to satisfy existing matching logic.

### Multiple bail actions

Extract the relevant chronology.

For the simple table:

- Include qualifying setting and modification-setting observations.
- Preserve revocation, denial, and other actions as context.
- Do not treat repeated amounts on revocation or denial rows as new setting observations.
- Do not select the largest or latest amount as the operative amount.
- Collapse exact duplicate representations of the same entry.
- Display distinct qualifying observations separately.

Keep source review and operative-order interpretation separate from discovery.

## 7. Event dates, row identity, and deduplication

“Hearing date” means the scheduled date of the event matching the submitted calendar criteria.

Never substitute:

- Filing date.
- Bail-action date.
- Arrest date.
- PDF print date.

Use validated calendar event data as the primary event source. Cross-check against the corresponding PDF event when identifiable.

An absent PDF event is not automatically a contradiction. A conflicting corresponding event must be reported and withheld pending resolution.

Preserve date-only values without timezone conversion changing the day.

### Internal representation

- Download each unique docket once per job.
- Preserve all distinct matching calendar events.
- Deduplicate identical events using date, type, time, and source identifier where available.
- Preserve each distinct qualifying bail-setting observation.
- Pair matching events with qualifying observations for display.

One displayed row represents:

```text
One matching event
+
one distinct qualifying monetary setting observation
```

Matching targets count distinct dockets, not displayed rows.

Keep legacy reports and checkpoints readable.

Retain per observation:

- Bail action.
- Action date.
- Bail category.
- Recorded amount in cents.
- Percentage when present.
- Accurate financial basis.
- One-based PDF page number.

Classify:

- Readable document without qualifying monetary bail.
- Unsupported layout.
- Ambiguous financial association.
- Image-only or unreadable document.
- Identity mismatch.
- Failed retrieval.

Do not collapse these into one no-match outcome.

## 9. Matching and filtering

Inspect existing collection and display predicates.

The reviewed frontend used a strict display comparison while new-job collection required an inclusive maximum. Correct that inconsistency for new searches.

For new searches:

- Maximum means less than or equal to.
- An existing minimum, if supported, means greater than or equal to.
- Missing amounts never satisfy a monetary comparison.
- No-bound monetary searches still require qualifying monetary observations.
- Percentages and posted-security amounts do not participate as replacement bail amounts.

Use one shared, tested definition for:

- Collection matching.
- Matching-docket counts.
- Main table projection.
- CSV selection.

Keep fixed collection criteria distinct from optional display-only narrowing.

Changing display filters must not change the collection target, original criteria, or budget.

Preserve legacy comparison semantics for legacy jobs and label them where relevant.

Default posted exclusion off in the simple search flow.
