The engine should operate as one deterministic pipeline:

`validate query → submit calendar form → classify response → extract docket rows → retrieve PDFs → verify identity → extract bail → apply filters → return results`

Keep discovery, extraction, interpretation, and filtering separate, as established in the functional scaffold.[1]

## 1. Submit calendar search

Use a real browser client such as Playwright because the calendar form may depend on JavaScript, dynamically populated controls, cookies, and browser state.

### Implementation

1. Open the configured public calendar URL.
2. Wait for the court, event, and date controls to become usable.
3. Select the court by its verified option value.
4. Wait for any dependent event list to finish updating.
5. Select `Bail Hearing`.
6. Fill the start and end dates in the format expected by the page.
7. Read all values back from the controls.
8. Reject the submission if the read-back values do not match the query.
9. Click the actual submit control.
10. Wait for navigation, a response, or a meaningful DOM change.

```ts
async function submitCalendarSearch(page, query, selectors) {
  await page.goto(selectors.calendarUrl, {
    waitUntil: "domcontentloaded"
  });

  await page.locator(selectors.court).waitFor({ state: "visible" });
  await page.selectOption(selectors.court, query.courtOptionValue);

  await waitForOption(
    page,
    selectors.event,
    query.eventOptionValue
  );

  await page.selectOption(
    selectors.event,
    query.eventOptionValue
  );

  await page.fill(selectors.startDate, formatCourtDate(query.startDate));
  await page.fill(selectors.endDate, formatCourtDate(query.endDate));

  const selected = await readCalendarControls(page, selectors);

  if (!sameSearch(selected, query)) {
    throw new SearchError("FORM_VALUES_DID_NOT_STICK");
  }

  const before = await pageFingerprint(page);

  await page.locator(selectors.submit).click();

  await waitForCalendarChange(page, before);

  return captureCalendarPage(page);
}
```

Replit must derive `selectors` and option values from the observed page. It should not invent field names or assume that visible labels equal submitted values.

## 2. Classify the response

Run a deterministic classifier against the post-submission DOM. Test the strongest and most specific conditions first.

### Classification order

1. Access-denial signature
2. Form-validation error
3. Validated results table
4. Explicit empty-result message
5. Submission not observed
6. Unvalidated response

```ts
function classifyCalendarPage(snapshot, signatures) {
  if (matchesAccessDenial(snapshot, signatures.accessDenied)) {
    return { status: "ACCESS_DENIED" };
  }

  const formErrors = findFormErrors(snapshot, signatures.formErrors);

  if (formErrors.length > 0) {
    return {
      status: "FORM_VALIDATION_ERROR",
      errors: formErrors
    };
  }

  const table = findResultsTable(snapshot, signatures.resultsTable);

  if (table && validateTableStructure(table)) {
    return {
      status: "RESULTS_VALIDATED",
      table
    };
  }

  if (matchesExplicitEmptyState(snapshot, signatures.emptyResult)) {
    return { status: "EMPTY_RESULTS_VALIDATED" };
  }

  if (!snapshot.submissionObserved) {
    return { status: "SUBMISSION_NOT_OBSERVED" };
  }

  return { status: "RESULTS_NOT_VALIDATED" };
}
```

A search form remaining on the page means nothing by itself. The engine must look below or beside the form for validated results, validation messages, or an explicit empty state.

## 3. Extract docket candidates

Only parse rows after the page reaches `RESULTS_VALIDATED`.

### Candidate model

```ts
interface CalendarCandidate {
  docketNumber: string;
  normalizedDocketNumber: string;
  court: string;
  eventType: string;
  eventDate: string;
  documentUrl: string;
  sourceRowIndex: number;
}
```

### Extraction process

1. Map table headers to column indexes by normalized header text.
2. Validate required columns before reading any rows.
3. Read each data row.
4. Extract the docket number, event, date, court, and link.
5. Resolve relative links against the calendar response URL.
6. Reject rows missing a valid docket number or document link.
7. Require the event to normalize to `Bail Hearing`.
8. Normalize the docket number.
9. Deduplicate by normalized docket number.
10. Preserve the first occurrence and original result order.

```ts
function extractCandidates(table, baseUrl) {
  const columns = mapCalendarColumns(table.headers);

  requireColumns(columns, [
    "docketNumber",
    "eventType",
    "eventDate",
    "documentLink"
  ]);

  const unique = new Map<string, CalendarCandidate>();

  for (const [index, row] of table.rows.entries()) {
    const candidate = parseCalendarRow(row, columns, baseUrl);

    if (!candidate) continue;
    if (normalizeEvent(candidate.eventType) !== "BAIL_HEARING") continue;
    if (!isValidDocumentUrl(candidate.documentUrl)) continue;

    const key = normalizeDocketNumber(candidate.docketNumber);

    if (!unique.has(key)) {
      unique.set(key, {
        ...candidate,
        normalizedDocketNumber: key,
        sourceRowIndex: index
      });
    }
  }

  return [...unique.values()];
}
```

Do not select columns by fixed numeric position unless the demonstrated layout proves the positions are stable.

## 4. Retrieve the PDF

The PDF worker receives only links extracted from validated calendar results.

### Retrieval process

1. Wait until the request scheduler permits the next transmission.
2. Request the calendar-discovered URL.
3. Follow the permitted redirect chain.
4. Record the final URL and response.
5. Require a successful HTTP status.
6. Check the declared content type.
7. Check that the body starts with the PDF signature `%PDF-`.
8. Reject HTML, empty responses, and malformed documents.
9. Pass the bytes and candidate identity to the identity validator.

```ts
async function retrievePdf(candidate, httpClient, scheduler) {
  await scheduler.acquire();

  const response = await httpClient.get(candidate.documentUrl, {
    redirect: "follow",
    responseType: "arraybuffer"
  });

  await scheduler.recordCompletion(response);

  if (response.status < 200 || response.status >= 300) {
    return failure(candidate, "PDF_HTTP_ERROR", response.status);
  }

  const bytes = Buffer.from(response.data);
  const contentType = response.headers["content-type"] ?? "";

  if (!bytes.subarray(0, 5).equals(Buffer.from("%PDF-"))) {
    return failure(candidate, "RESPONSE_NOT_PDF", contentType);
  }

  if (!pdfCanBeOpened(bytes)) {
    return failure(candidate, "MALFORMED_PDF");
  }

  return {
    status: "PDF_RETRIEVED",
    candidate,
    bytes,
    finalUrl: response.finalUrl
  };
}
```

The PDF signature check is important because an access page can return HTML with a successful status.

## 5. Verify docket identity

Extract text from the PDF before attempting bail extraction.

### Identity process

1. Use a PDF text extractor such as PDF.js or an equivalent library.
2. Inspect the demonstrated docket-identification region.
3. Find strings matching the supported docket-number pattern.
4. Normalize each discovered number.
5. Compare it with the normalized calendar docket number.
6. Continue only if there is one clear match.

```ts
function verifyPdfIdentity(pdfText, candidate, docketPattern) {
  const found = extractDocketNumbers(pdfText, docketPattern)
    .map(normalizeDocketNumber);

  const unique = [...new Set(found)];
  const expected = candidate.normalizedDocketNumber;

  if (unique.includes(expected)) {
    return {
      status: "IDENTITY_VERIFIED",
      docketNumber: expected
    };
  }

  if (unique.length === 0) {
    return {
      status: "IDENTITY_UNREADABLE"
    };
  }

  return {
    status: "IDENTITY_MISMATCH",
    expected,
    found: unique
  };
}
```

Do not use a party name as the primary match. The normalized docket number should join the calendar row to the PDF.

## 6. Extract bail entries

Use a layout adapter for each demonstrated PDF layout. Do not run broad keyword matching across the entire document.

### Layout identification

Create a signature from:

- Required section heading
- Required column headings
- Relative ordering of headings
- Minimum expected fields
- Text-bearing versus scanned document

```ts
function identifyBailLayout(document) {
  for (const adapter of registeredBailAdapters) {
    if (adapter.matches(document)) {
      return adapter;
    }
  }

  return null;
}
```

### Table reconstruction

PDFs often store words by coordinates rather than as real HTML-style tables. Reconstruct rows using each text span’s page, vertical position, and horizontal position:

1. Extract text spans with \(x\) and \(y\) coordinates.
2. Find the demonstrated bail-section heading.
3. Limit extraction to that section.
4. Group spans with similar vertical coordinates into rows.
5. Assign spans to columns using demonstrated horizontal boundaries.
6. Normalize whitespace without changing substantive text.
7. Parse each reconstructed row.

```ts
function reconstructRows(spans, layout) {
  const section = cropToSection(spans, layout.sectionBounds);
  const visualRows = groupByVerticalPosition(
    section,
    layout.rowTolerance
  );

  return visualRows.map(row =>
    assignSpansToColumns(row, layout.columns)
  );
}
```

### Entry model

```ts
interface BailEntry {
  category:
    | "MONETARY"
    | "NONMONETARY"
    | "UNSECURED"
    | "NOMINAL"
    | "UNKNOWN";

  basis:
    | "TOTAL_BAIL"
    | "DEPOSIT"
    | "OTHER"
    | "UNKNOWN";

  amountCents: number | null;
  entryType: string | null;
  entryDate: string | null;
  postedState: "SHOWN_POSTED" | "NOT_SHOWN" | "UNKNOWN";
  sourceText: string;
}
```

### Bail parsing

```ts
function extractBailEntries(document) {
  const adapter = identifyBailLayout(document);

  if (!adapter) {
    return { status: "UNSUPPORTED_LAYOUT", entries: [] };
  }

  const rows = adapter.reconstructRows(document.textSpans);
  const entries = [];

  for (const row of rows) {
    const parsed = adapter.parseRow(row);

    if (parsed.status === "AMBIGUOUS") {
      return {
        status: "AMBIGUOUS_BAIL_SECTION",
        entries: []
      };
    }

    if (parsed.basis === "DEPOSIT") {
      return {
        status: "UNSUPPORTED_DEPOSIT_LAYOUT",
        entries: []
      };
    }

    entries.push(parsed.entry);
  }

  return {
    status: "BAIL_EXTRACTED",
    entries
  };
}
```

The earlier parser separated monetary bail from fees, fines, unsecured bail, nonmonetary bail, and zero-dollar entries; that same separation must remain in the automated extractor.[2]

## 7. Produce `TOTAL_BAIL`

Do not calculate a total by adding every currency value appearing in the document. Use only a row explicitly identified by the supported adapter as the total bail amount.

### Amount parsing

Convert currency directly into integer cents:

```ts
function parseMoneyToCents(raw: string): number | null {
  const normalized = raw
    .replace(/\$/g, "")
    .replace(/,/g, "")
    .trim();

  if (!/^\d+(\.\d{1,2})?$/.test(normalized)) {
    return null;
  }

  const [dollars, fraction = ""] = normalized.split(".");
  const cents = fraction.padEnd(2, "0");

  return Number(dollars) * 100 + Number(cents);
}
```

### Total selection

```ts
function determineTotalBail(entries: BailEntry[]) {
  const totals = entries.filter(entry =>
    entry.category === "MONETARY" &&
    entry.basis === "TOTAL_BAIL" &&
    Number.isInteger(entry.amountCents)
  );

  const distinctAmounts = [
    ...new Set(totals.map(entry => entry.amountCents))
  ];

  if (distinctAmounts.length === 0) {
    return {
      status: "TOTAL_BAIL_UNAVAILABLE",
      totalBailCents: null
    };
  }

  if (distinctAmounts.length > 1) {
    return {
      status: "TOTAL_BAIL_AMBIGUOUS",
      totalBailCents: null
    };
  }

  return {
    status: "TOTAL_BAIL_SUPPORTED",
    totalBailCents: distinctAmounts[0]
  };
}
```

If multiple bail events produce different totals and the adapter cannot unambiguously select the relevant event, return ambiguity rather than choosing the newest-looking number.

## 8. Apply the filters

Perform filtering after extraction and use integer cents for monetary comparison.

```ts
function matchesQuery(record, query) {
  if (record.eventType !== "BAIL_HEARING") return false;

  if (!dateWithinInclusiveRange(
    record.eventDate,
    query.startDate,
    query.endDate
  )) {
    return false;
  }

  if (query.maximumBailCents !== null) {
    if (record.totalBailStatus !== "TOTAL_BAIL_SUPPORTED") {
      return false;
    }

    if (record.totalBailCents > query.maximumBailCents) {
      return false;
    }
  }

  if (
    query.excludeShownPosted &&
    record.postedState === "SHOWN_POSTED"
  ) {
    return false;
  }

  return true;
}
```

For new jobs, equality passes:

```text
total bail <= maximum bail
```

For legacy jobs that retain strict comparison:

```text
total bail < maximum bail
```

Store the comparison mode in the job when it is created so its behavior cannot change while it runs.

## 9. Process available candidates

Use one background worker with a stable queue.

### Candidate state machine

```text
DISCOVERED
    ↓
PDF_RETRIEVED
    ↓
IDENTITY_VERIFIED
    ↓
BAIL_EXTRACTED
    ↓
MATCHED or NOT_MATCHED
```

Possible exits:

```text
RETRIEVAL_FAILED
IDENTITY_MISMATCH
IDENTITY_UNREADABLE
UNSUPPORTED_LAYOUT
AMBIGUOUS_BAIL_SECTION
UNSUPPORTED_DEPOSIT_LAYOUT
```

### Worker loop

```ts
async function processCandidates(job, candidates) {
  for (const candidate of candidates) {
    if (job.matchCount >= job.targetMatches) {
      return finish(job, "TARGET_REACHED");
    }

    if (job.processedCount >= job.recordCap) {
      return finish(job, "RECORD_CAP_REACHED");
    }

    if (!job.requestBudget.canSpend(1)) {
      return finish(job, "REQUEST_CAP_REACHED");
    }

    const pdf = await retrievePdf(
      candidate,
      job.httpClient,
      job.scheduler
    );

    if (pdf.status !== "PDF_RETRIEVED") {
      await saveCandidateFailure(job, candidate, pdf.status);
      continue;
    }

    const document = await parsePdf(pdf.bytes);
    const identity = verifyPdfIdentity(
      document.text,
      candidate,
      job.docketPattern
    );

    if (identity.status !== "IDENTITY_VERIFIED") {
      await saveCandidateFailure(job, candidate, identity.status);
      continue;
    }

    const extraction = extractBailEntries(document);

    if (extraction.status !== "BAIL_EXTRACTED") {
      await saveCandidateFailure(
        job,
        candidate,
        extraction.status
      );
      continue;
    }

    const total = determineTotalBail(extraction.entries);
    const record = buildSearchRecord(
      candidate,
      extraction,
      total
    );

    await saveProcessedRecord(job, record);

    if (matchesQuery(record, job.query)) {
      await saveMatch(job, record);
    }
  }

  return finish(job, "VALIDATED_ROWS_EXHAUSTED");
}
```

A nonmatch is not a failure. The worker continues until it reaches the match target or runs out of validated candidates or processing capacity.

### Pagination

After processing the current page:

1. Look for the demonstrated enabled “next” control.
2. Capture the current page fingerprint.
3. Activate “next.”
4. Wait for the fingerprint to change.
5. Classify the new page.
6. Extract and deduplicate new candidates.
7. Stop if the page repeats, the next control is absent, or validation fails.

```ts
while (calendarPage.hasValidatedNextPage) {
  const previous = calendarPage.fingerprint;
  calendarPage = await goToNextCalendarPage();

  if (calendarPage.fingerprint === previous) {
    return finish(job, "PAGINATION_CYCLE_DETECTED");
  }

  const state = classifyCalendarPage(calendarPage);

  if (state.status !== "RESULTS_VALIDATED") {
    return finish(job, "PAGINATION_NOT_VALIDATED");
  }

  enqueueNewCandidates(
    extractCandidates(state.table),
    seenDocketNumbers
  );
}
```

Until this behavior is demonstrated, the engine should process only the validated first page and return `PAGINATION_INCOMPLETE`.

## Complete control flow

```ts
async function runSearch(job) {
  validateSupportedQuery(job.query);

  const calendarSnapshot = await submitCalendarSearch(
    job.browserPage,
    job.query,
    job.calendarAdapter
  );

  const calendarState = classifyCalendarPage(
    calendarSnapshot,
    job.calendarAdapter.signatures
  );

  if (calendarState.status === "EMPTY_RESULTS_VALIDATED") {
    return finish(job, "EMPTY_RESULTS_VALIDATED");
  }

  if (calendarState.status !== "RESULTS_VALIDATED") {
    return finish(job, calendarState.status);
  }

  const candidates = extractCandidates(
    calendarState.table,
    calendarSnapshot.finalUrl
  );

  await saveCandidates(job, candidates);

  return processCandidates(job, candidates);
}
```

That is how the engine works mechanically: **the browser obtains a validated calendar response; the calendar parser produces docket candidates; the PDF client retrieves each document; the identity validator confirms the docket; the layout adapter extracts bail; the filter selects matches; and the API returns the accumulated results.**

The deeper task is to eliminate the hidden failure modes that make an implementation *look* correct while silently missing submissions, issuing uncounted requests, parsing the wrong table, or matching the wrong bail entry.

The strongest design is an **evidence-carrying state machine**: every stage must return both a value and proof that the value came from the intended source state.

## 1. Make submission transactional

The current failure may not be “the form came back.” The real problem could be that a dependent control reset, the selected option never stuck, a hidden field became stale, or submission produced no observable transition.

### Build it this way

1. Read the available court options from the live DOM.
2. Select the court using its observed option value.
3. Wait for the event control to repopulate.
4. Confirm that `Bail Hearing` now exists.
5. Select it and read the selected value back.
6. Enter the dates.
7. Blur or tab out of each date field so any change handlers execute.
8. Read all four controls back after the page has settled.
9. Create a normalized `submittedQuery` from those read-back values.
10. Reject the operation if `submittedQuery` differs from the job query.
11. Submit using the visible control a user would use.
12. Capture evidence that submission happened.

Playwright’s locator actions already wait for controls to be visible and enabled, while `selectOption()` waits for the specified option and emits the relevant input and change events. Do not use `force: true` to conceal a disabled or obstructed control.[1][2]

### Submission evidence

Require at least one of these:

- A matching browser request began after the submit action.
- The document URL changed.
- A form-generation token changed.
- A known results container appeared.
- A known validation container appeared.
- A postback-specific DOM region changed.

Do not use “the click method returned” as proof.

### Hidden problem to anticipate

Selecting the court may replace the entire event `<select>` element. If Replit stores an element handle before selecting the court, it may subsequently interact with a detached control.

**Solution:** Store locator definitions, not element handles. Resolve each locator again after every action that can rerender the form.

## 2. Wait for an outcome

`networkidle` is not a reliable definition of search completion. A page can maintain background requests, finish without navigating, update only part of the DOM, or return a form and results together.

### Use an outcome race

After submission, wait for the first valid terminal signal:

```ts
await Promise.race([
  waitForValidatedResults(page),
  waitForExplicitEmptyState(page),
  waitForFormValidationError(page),
  waitForAccessDenial(page),
  waitForUnexpectedDocument(page),
  waitForDeadline()
]);
```

A terminal signal must remain stable for a short settling interval. This prevents the engine from classifying a transient skeleton table, loading message, or briefly displayed validation container.

### Use classifier precedence

Evaluate states in this order:

1. `ACCESS_DENIED`
2. `FORM_VALIDATION_ERROR`
3. `RESULTS_VALIDATED`
4. `EMPTY_RESULTS_VALIDATED`
5. `SUBMISSION_NOT_OBSERVED`
6. `RESULTS_NOT_VALIDATED`

Access denial goes first because an access page might contain generic words such as “search” or “no results.” Validated results precede empty results because some pages retain an old or hidden empty-state element in the DOM.

### Bind results to the query

A structurally valid table is not enough. Require evidence that the page represents the submitted search through one or more of:

- Echoed court
- Echoed event
- Echoed dates
- Submission-response identity
- Results-container generation after the recorded submission

Otherwise, a stale table from a previous job could be accepted.

## 3. Resolve request serialization

The current contract creates a subtle engineering problem: a normal browser may request the document, scripts, styles, fonts, and other assets concurrently, while the application promises concurrency one and a delay measured from the preceding response’s completion.

### Put every transmission behind one scheduler

Use browser request routing to intercept all requests before transmission. Playwright routing stalls matching requests until the handler explicitly continues, fulfills, or aborts them.[3]

```ts
await context.route("**/*", async route => {
  const request = route.request();

  if (!assetPolicy.isRequired(request)) {
    return route.abort("blockedbyclient");
  }

  const reservation = await scheduler.reserve(request);

  if (!reservation.approved) {
    return route.abort("blockedbyclient");
  }

  await scheduler.waitUntilAllowed(reservation);
  await route.continue();
});
```

The scheduler must be global to the source, not local to one page or worker.

### Release only after completion

The transmission slot remains occupied until the request:

- Finishes successfully
- Fails
- Times out with uncertain transmission

Then persist:

```text
next_allowed_at =
    response_finished_at + configured_interval
```

Do not calculate the next time from request start. A slow response would otherwise overlap the next transmission.

### Anticipate browser-generated traffic

Intercept and classify:

- Main documents
- JavaScript
- Stylesheets
- Fonts
- Images
- Favicons
- Prefetches
- Redirects
- PDF requests
- Requests initiated by service workers

Block service workers and speculative requests unless they are demonstrated requirements. Otherwise, traffic can bypass the accounting model.

### Detect an impossible contract

Some pages require multiple assets to load in parallel or expect dependencies before a timeout. If serializing all required assets prevents the calendar from initializing, the engine must return:

```text
BROWSER_REQUEST_MODEL_INCOMPATIBLE
```

It must not silently abandon concurrency one or pretend the form is broken.

## 4. Validate tables semantically

A selector such as `table.results` is too weak. It can match empty shells, hidden desktop/mobile duplicates, unrelated tables, or a changed layout with the same class.

### Use a table contract

A results table is valid only when all required invariants hold:

```ts
interface CalendarTableContract {
  requiredHeaders: HeaderRule[];
  minimumDataRows: number;
  docketColumn: ColumnRule;
  eventColumn: ColumnRule;
  dateColumn: ColumnRule;
  linkRule: LinkRule;
}
```

Validate:

- One visible candidate table
- Required headers exactly or through approved aliases
- At least one non-template row
- Parseable docket number
- Parseable date
- Expected event text
- Usable docket or document link
- No loading or placeholder state

### Do not deduplicate too early

The same docket may appear more than once because it has multiple calendar rows. Preserve raw event rows first:

```ts
CalendarEventCandidate {
  docketNumber,
  eventType,
  eventDate,
  courtroom,
  sourceRow,
  documentLink
}
```

Then create one processing candidate per docket while retaining all contributing calendar events. If Replit deduplicates immediately, it may discard the row containing the usable link or correct hearing date.

### Handle hidden duplicate tables

Responsive sites sometimes render separate mobile and desktop tables. Filter candidates by visibility, meaningful row count, and structural validity before choosing one.

If two visible tables independently satisfy the contract but disagree, return `MULTIPLE_RESULTS_TABLES` instead of selecting the first.

## 5. Treat document links as opaque

Do not rebuild, simplify, normalize, or guess PDF URLs. Query parameters may contain document identifiers, temporary values, or routing information.

### Retrieval sequence

1. Preserve the extracted link exactly.
2. Resolve only relative-versus-absolute addressing.
3. Send one request through the shared scheduler.
4. Record every redirect as a separate request.
5. Validate final status and response body.
6. Hash the complete bytes.
7. Pass the bytes—not the URL—to the PDF parser.

### Avoid hidden PDF requests

PDF.js can load documents in chunks by default. If Replit gives PDF.js a URL, PDF.js may generate additional range or streaming requests that bypass the expected “one PDF request” model.[4]

Instead:

```ts
const bytes = await controlledPdfDownload(url);

const task = pdfjs.getDocument({
  data: new Uint8Array(bytes),
  disableRange: true,
  disableStream: true,
  disableAutoFetch: true
});
```

This ensures parsing operates on the already-accounted-for response.

### Validate more than MIME type

Accept a document only if:

- The response status is successful.
- The body begins with a valid PDF signature.
- The body is not merely an HTML page mislabeled as PDF.
- PDF.js can open the file.
- At least one page exists.
- The file is not truncated.
- The document is not encrypted beyond the parser’s ability to read it.

An `application/pdf` header alone is insufficient.

***

## 6. Verify primary identity

Searching the entire PDF for the expected docket number is vulnerable to false matches. A document can mention another docket in related-case text, captions, notes, or attachments.

### Anchor identity to the header

The identity adapter should define:

- Expected page
- Expected docket-header label
- Expected region around that label
- Supported docket pattern
- Normalization rules

Require the expected docket number to appear in the demonstrated primary header region, not merely somewhere in the PDF.

```ts
function verifyPrimaryIdentity(document, expected) {
  const firstPage = document.pages[0];
  const headerRegion = crop(firstPage, layout.docketHeaderBounds);
  const identified = parseDocketHeader(headerRegion);

  if (identified.length !== 1) {
    return "PRIMARY_IDENTITY_AMBIGUOUS";
  }

  return normalize(identified[0]) === normalize(expected)
    ? "IDENTITY_VERIFIED"
    : "IDENTITY_MISMATCH";
}
```

### Preserve meaningful components

Parse docket identity into components rather than stripping every non-alphanumeric character:

```ts
{
  courtLevel,
  judicialDistrict,
  caseType,
  sequenceNumber,
  year
}
```

Compare every required component. Overaggressive normalization can make two malformed identifiers appear equal.

### Handle multi-document packets

If the first page establishes the expected docket but later pages contain other docket sheets, do not treat the entire file as one supported document. Either isolate the page range belonging to the verified docket or return `MULTI_DOCKET_PACKET_UNSUPPORTED`.

***

## 7. Reconstruct PDF tables robustly

PDF text is not necessarily stored in reading order. PDF.js exposes each text item’s string, transformation matrix, width, height, direction, and line-ending indication. Use those coordinates rather than concatenating extracted strings.[5]

### Normalize coordinates first

Before grouping rows:

1. Apply the page viewport transformation.
2. Normalize page rotation.
3. Convert coordinates into one consistent top-to-bottom system.
4. Scale relative to page width and height.
5. Sort by normalized page, vertical baseline, then horizontal position.

### Reconstruct rows in stages

```text
text items
→ normalized positioned tokens
→ baseline clusters
→ column assignments
→ logical rows
→ bail entries
```

Use adaptive baseline tolerance based on median text height, rather than one hardcoded pixel value. Fixed tolerances often fail when the same layout is rendered at a different scale.

### Anticipate split tokens

A monetary amount may arrive as:

```text
"$"
"5"
","
"000"
"."
"00"
```

Join adjacent tokens only when:

- They occupy the same logical row.
- Their horizontal gap is below the adapter threshold.
- The resulting token satisfies the strict money grammar.
- They remain inside the amount column.

Do not globally concatenate text.

### Handle wrapped rows

If a description wraps onto a second visual line:

- Start a logical row when the key column is populated.
- Attach continuation lines only when their key columns are empty.
- Stop at the next populated key column.
- Reject a continuation that crosses into another table section.

### Define section boundaries

Start at the demonstrated `Bail Set` heading and stop at:

- The next recognized section heading
- The adapter’s demonstrated table terminator
- The end of the supported page range

A keyword located elsewhere in the docket must not start bail extraction.

PDF.js normalizes whitespace in `getTextContent()`, so layout matching should not depend on unusual whitespace characters.[6]

***

## 8. Require layout invariants

Do not choose whichever adapter achieves the highest fuzzy score. A bad “best match” is still a bad match.

### Each adapter should require

- Correct section heading
- Correct required columns
- Correct column ordering
- Parseable row structure
- Supported bail category vocabulary
- Supported amount basis
- No unresolved deposit field
- No conflicting table boundaries

```ts
const result = adapter.inspect(document);

if (!result.allRequiredInvariantsPass) {
  return {
    status: "UNSUPPORTED_LAYOUT",
    failedInvariants: result.failedInvariants
  };
}
```

### Save field-level evidence

Each extracted value should retain the source spans that produced it:

```ts
ExtractedField<number> {
  value: 500000,
  page: 3,
  boundingBoxes: [...],
  sourceTokens: ["$", "5,000.00"],
  adapterVersion: "cp-bail-v1"
}
```

This makes parser errors reproducible. Without field-level evidence, Replit will know that a value is wrong but not which row-construction decision caused it.

### Test false-positive resistance

The parser must not produce `TOTAL_BAIL` when:

- A fee elsewhere in the document contains a dollar amount.
- A percentage deposit appears near a monetary amount.
- The table has an unfamiliar extra column.
- A total is split across conflicting rows.
- The bail category is missing.
- A previous and later entry disagree without supported selection semantics.

The earlier parser specifically needed to distinguish monetary bail from fees, unsecured bail, nonmonetary bail, and zero-dollar entries.[7]

***

## 9. Define matching precisely

The phrase “docket has bail below the maximum” becomes ambiguous when a docket contains multiple bail observations.

### Use observation-based matching

For the current stated behavior, a docket matches when it contains at least one supported observation satisfying:

```text
category = MONETARY
basis = TOTAL_BAIL
amount is known in whole cents
amount <= maximum for new jobs
```

Store the specific observation that caused the match:

```ts
MatchEvidence {
  docketNumber,
  bailEntryId,
  amountCents,
  entryDate,
  comparisonMode,
  maximumCents
}
```

Do not reduce multiple observations to a synthetic minimum and display that minimum as “the bail.” Return the qualifying observation or observations, while counting the docket once.

### Version the comparator

```ts
function amountMatches(amount, maximum, mode) {
  return mode === "LTE_V2"
    ? amount <= maximum
    : amount < maximum;
}
```

Persist `comparisonMode` inside the job. Never derive it from the current application version when resuming an older job.

### Keep posted filtering independent

Only the explicit state `SHOWN_POSTED` should trigger exclusion. `UNKNOWN`, missing section, extraction failure, and absence of demonstrated posted evidence must remain distinct.

***

## 10. Make the worker crash-safe

Concurrency one does not prevent duplicate requests. A worker can transmit a request, receive the response, crash before saving completion, restart, and send the same request again.

### Use an append-only request ledger

Before transmission, atomically create:

```ts
RequestAttempt {
  id,
  jobId,
  purpose,
  targetFingerprint,
  state: "RESERVED",
  reservedAt,
  startedAt: null,
  completedAt: null
}
```

Transitions:

```text
RESERVED
→ TRANSMITTING
→ COMPLETED

RESERVED
→ CANCELLED_BEFORE_TRANSMISSION

TRANSMITTING
→ FAILED_CONFIRMED

TRANSMITTING
→ OUTCOME_UNCERTAIN
```

On restart, never automatically replay `TRANSMITTING` or `OUTCOME_UNCERTAIN`. Require the worker to stop with the preserved partial results.

### Use compare-and-swap transitions

A candidate can advance only from its expected current state:

```sql
UPDATE candidates
SET state = 'PDF_RETRIEVED'
WHERE id = ?
  AND state = 'PDF_REQUESTED';
```

If zero rows change, another worker or a previous execution already advanced it. Do not repeat the network operation.

### Calculate counts from records

Do not maintain progress solely through increment statements such as `processed_count += 1`. Crashes and duplicate handlers can corrupt them.

Calculate or reconcile:

- Discovered from candidate records
- Processed from terminal candidate states
- Matching from unique match records
- Failed from classified failure states
- Unprocessed from nonterminal candidates

Add database uniqueness constraints for:

```text
(job_id, normalized_docket_number)
(job_id, normalized_docket_number, matched_bail_entry_id)
(request_attempt_id)
```

***

## 11. Make pagination provable

A “next” button is not proof that a new page loaded. It may be disabled, rerender the same rows, wrap around, or require hidden form state.

### Fingerprint each page

Create a fingerprint from:

- Normalized docket numbers in order
- Visible page number, if available
- Next-control state
- Relevant hidden pagination state

After activating “next,” require the fingerprint to change.

```ts
if (newFingerprint === previousFingerprint) {
  return "PAGINATION_DID_NOT_ADVANCE";
}

if (seenFingerprints.has(newFingerprint)) {
  return "PAGINATION_CYCLE_DETECTED";
}
```

### Deduplicate across pages

Maintain both:

- Seen event-row keys
- Seen docket keys

This prevents repeated pages from creating duplicate PDF requests while still preserving multiple distinct Bail Hearing rows for the same docket.

### Stop honestly

Pagination is complete only when the demonstrated terminal condition appears, such as a disabled or absent next control after a validated page. Anything else remains `PAGINATION_INCOMPLETE`.

***

## 12. Build a replay laboratory

The fastest way to improve this tool is not repeated live probing. It is reproducing the complete browser-to-result pipeline from saved artifacts without network access.

### Save a replay bundle

For each approved diagnostic run, retain:

```text
query.json
browser-actions.json
network-ledger.json
post-submit.html
post-submit-screenshot.png
calendar-response-metadata.json
calendar-candidates.json
document.pdf
expected-result.json
```

The replay runner feeds those artifacts through the same production validators and parsers.

### Add mutation tests

Take a known fixture and change exactly one property:

- Rename one required calendar header.
- Remove the docket link.
- Duplicate a calendar row.
- Split the dollar amount into additional PDF tokens.
- Move a fee into a nearby column.
- Add a second conflicting total.
- Change the expected docket number by one digit.
- Replace the PDF with HTML.
- Repeat the same pagination fingerprint.
- Change the maximum by one cent.

Every mutation should either preserve the correct result or produce a specific failure state.

### Add invariant tests

The following must always hold:

```text
matching <= processed <= discovered
failed + matched + nonmatched + unsupported = processed
each docket contributes at most one match count
no PDF request exists without a validated candidate
no extraction exists without verified identity
no result exists without an extracted qualifying observation
```

Fail the job immediately if an invariant is violated.

## Immediate repair sequence

For the currently paused implementation, Replit should work in this order:

1. Inspect whether the court selection caused the event control to be replaced or reset.
2. Determine whether a submission request was actually observed.
3. Compare the pre-submit and post-submit DOM fingerprints.
4. Check whether request blocking prevented a required script from populating or submitting the form.
5. Replace `RETURNED_FORM` with the ordered outcome classifier.
6. Route every browser transmission through the global scheduler.
7. Build a replay fixture from the failed page.
8. Make the fixture produce one precise diagnostic state.
9. Add mutations for form-plus-results, explicit empty results, and access denial.
10. Only then perform the next bounded search.

The crucial upgrade is not another selector or another retry. It is making every stage answer three questions: **What state did I observe? What evidence proves it? What exact state transition is permitted next?**
