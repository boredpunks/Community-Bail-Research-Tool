Below is the functional scaffold: the application’s modules, data structures, search contract, processing pipeline, and API boundaries—without the visual theme. It is designed to work first with manually entered or imported records, then accept live-source adapters without changing the search engine.

This is an implementation blueprint, not a claim that source integrations already exist.

### Module responsibilities

| Module | Responsibility | Must not do |
|---|---|---|
| Search service | Filter saved observations and assemble results. | Pretend saved records are a countywide search. |
| Discovery service | Coordinate enabled source queries. | Infer custody from discoveries. |
| Import service | Validate, preview, and commit imports. | Mark imported assertions verified automatically. |
| Extraction service | Produce proposed bail observations. | Decide identity or release eligibility. |
| Identity service | Manage evidence-supported person/case links. | Merge people by name alone. |
| Bail projection | Select the appropriate displayed bail state. | Treat the latest number as automatically operative. |
| Custody projection | Evaluate documented custody and freshness. | Turn absence of information into release. |
| Review service | Record field-specific decisions and corrections. | Rewrite original evidence silently. |
| Export service | Export the defined result set safely. | Export unfiltered or unauthorized data. |
| Retention service | Apply configured deletion and suppression rules. | Claim downloaded copies can be recalled. |

## 2. Core data model

The foundation is an **observation** model: source evidence is retained separately from the application’s interpretation.

### Database tables

| Table | Essential fields |
|---|---|
| `users` | ID, authentication subject, role, active status |
| `sources` | ID, name, official URL, access method, capability status, enabled state, restrictions |
| `cases` | ID, docket number, court level, county, suppression state |
| `case_links` | Two case IDs, relationship, evidence reference, review decision |
| `people` | Internal ID, minimum authorized identity details |
| `person_case_links` | Person ID, case ID, supporting evidence, review state |
| `source_observations` | Source ID, locator, retrieval time, source time, time precision, minimal excerpt, parser version |
| `calendar_events` | Case ID, source observation ID, event type, date/time, event status |
| `bail_observations` | Case ID, source observation ID, original wording, category, amount, order date, action, deposit details, posted-entry state |
| `custody_observations` | Person or case reference, source observation ID, facility, custody state, observation time |
| `bail_interpretations` | Case ID, selected bail observation, interpretation status, supporting history, review reference |
| `review_decisions` | Target entity, field group, decision, reviewer, timestamp, correction reference |
| `import_batches` | File metadata, import type, validation status, committed count, rejected count |
| `jobs` | Job type, state, parameters, checkpoint, progress, cancellation flag |
| `job_source_runs` | Job ID, source ID, outcome, counts, pagination state, errors |
| `source_controls` | Source ID, pause state, resume-after time, request policy |
| `audit_events` | Actor, action, entity reference, timestamp, minimal metadata |
| `export_requests` | Actor, search snapshot, columns, state, expiry time |

Keep person records optional. A case can exist without a resolved person identity.

### Required constraints

```text
Unique case:
    county + court level + docket number

Money:
    nullable integer cents
    never floating-point
    amount must be nonnegative when present

Deposit percentage:
    nullable exact decimal
    validated range when present

Observation identity:
    source observation references must exist

Custody target:
    must reference a person, a case, or both
    unresolved case-level evidence must not become a person match

Review:
    must reference the exact observation or interpretation reviewed

Corrections:
    create a new version or superseding decision
    preserve original observation

Deletion:
    do not cascade away required evidence without an explicit,
    documented retention operation
```

## 3. Search and processing contracts

### Saved-record search

A saved-record search is read-only. It does not trigger background collection.

```ts
interface SavedSearchRequest {
  docketNumber?: string;
  nameCandidate?: string;

  courtLevels?: CourtLevel[];
  bailCategories?: BailCategory[];

  minimumAmountCents?: number;
  maximumAmountCentsExclusive?: number;

  amountBasis:
    | "LATEST_OBSERVED"
    | "REVIEWED_OPERATIVE";

  custodyStates?: CustodyDisplayState[];
  reviewGroupsRequired?: ReviewFieldGroup[];

  eventTypes?: string[];
  eventFrom?: string;
  eventToExclusive?: string;

  cursor?: string;
  pageSize: number;

  sort:
    | "DOCKET_ASC"
    | "AMOUNT_ASC"
    | "AMOUNT_DESC"
    | "RETRIEVED_DESC";
}
```

The `amountBasis` field prevents an unresolved latest observation from being confused with reviewed operative bail.

### Discovery request

Live discovery is a separate, explicit job.

```ts
interface DiscoveryRequest {
  sourceIds: string[];

  query: {
    docketNumber?: string;
    nameCandidate?: string;
    courtLevels?: CourtLevel[];
    eventTypes?: string[];
    from?: string;
    toExclusive?: string;
  };

  limits: {
    maximumRequests: number;
    maximumRecords: number;
  };
}
```

Do not accept amount filters as upstream source queries unless the selected adapter explicitly supports them.

### Search response

```ts
interface SearchResponse {
```


All adapter network calls must pass through the shared source limiter and allowlisted fetch layer.

### Processing pipeline

```text
Record entered, imported, or discovered
                │
                ▼
Validate docket and source metadata
                │
                ▼
Create or locate case
                │
                ▼
Retrieve or accept supporting evidence
                │
                ▼
Validate document identity
                │
                ▼
Extract proposed observations
                │
                ▼
Persist provenance and extraction status
                │
                ▼
Build provisional display projection
                │
                ▼
Human field-specific review
                │
                ▼
Update reviewed display projection
                │
                ▼
Search / evidence view / export
```

Custody evidence enters a parallel branch:

```text
Custody evidence supplied
        │
        ▼
Validate source, facility, and observation time
        │
        ▼
Resolve person/case association
        │
        ├── Ambiguous → unresolved evidence
        │
        ▼
Persist custody observation
        │
        ▼
Human review
        │
        ▼
Derive custody display state at search time
```

### Projection rules

The search engine reads projections, not arbitrary raw PDF text.

```text
BAIL PROJECTION

If reviewed operative interpretation exists:
    display its referenced observation
Else:
    display latest identifiable observation as provisional
    mark order interpretation unreviewed or unresolved

Never promote provisional amounts to reviewed operative amounts.

CUSTODY PROJECTION

If material evidence conflicts:
    display CONFLICTING

Else if a later supported release/transfer observation exists:
    display that disposition

Else if reviewed ACJ custody evidence has a usable observation time:
    compare that time with configured freshness window

Else:
    display UNKNOWN or OLDER_EVIDENCE as appropriate
```

If chronology cannot be established, do not resolve a conflict by retrieval time alone.

## 4. API and workflow boundaries

### API routes

All routes require authentication unless explicitly designated for authentication or a non-sensitive health check.

| Method and route | Function |
|---|---|
| `GET /api/session` | Return authenticated user and permissions. |
| `GET /api/sources` | Return source capabilities and availability. |
| `POST /api/search` | Search saved records. |
| `POST /api/discovery-jobs` | Start a bounded discovery job. |
| `GET /api/jobs/:id` | Read job progress and source outcomes. |
| `POST /api/jobs/:id/cancel` | Request cancellation. |
| `POST /api/jobs/:id/resume` | Resume an eligible paused job with authorization. |
| `POST /api/cases` | Enter a case manually. |
| `GET /api/cases/:id` | Retrieve authorized case details and projections. |
| `GET /api/cases/:id/evidence` | Retrieve minimal supporting evidence. |
| `POST /api/cases/:id/bail-observations` | Add a source-backed bail observation. |
| `POST /api/custody-observations` | Add documented custody evidence. |
| `POST /api/identity-links` | Propose an evidence-supported identity link. |
| `POST /api/imports/preview` | Validate an upload without committing records. |
| `POST /api/imports/:id/commit` | Commit a reviewed import preview. |
| `POST /api/reviews` | Record a field-specific review decision. |
| `POST /api/cases/:id/suppress` | Suppress a disputed record with a reason. |
| `POST /api/exports` | Create a scoped, authorized CSV export. |
| `GET /api/exports/:id/download` | Download an authorized, unexpired export. |
| `PATCH /api/admin/settings` | Update approved operating settings. |
| `POST /api/admin/sources/:id/pause` | Disable collection for a source. |
| `GET /api/admin/audit` | Inspect minimal audit history. |

### Import workflow

```text
Upload
  → validate file
  → identify import type
  → map columns if necessary
  → preview accepted/rejected rows
  → show duplicate and identity warnings
  → user commits
  → create observations
  → queue supported extraction
  → show import summary
```

Supported initial import types:

- Docket PDF.
- Case-list CSV.
- Bail-observation CSV.
- Authorized custody-observation CSV.

Do not guess an import’s meaning from ambiguous columns. Require a confirmed mapping.

Committing the same batch twice must not create duplicate observations.

### Export workflow

```text
Search
  → preserve search criteria and evaluation time
  → request export
  → authorize access
  → materialize a consistent result snapshot
  → sanitize textual cells
  → generate CSV
  → provide expiring authenticated download
  → record minimal audit event
```

An export must not silently include new observations added after its snapshot was created.

### Job behavior

```text
QUEUED → RUNNING → COMPLETED
                 → PARTIAL
                 → FAILED
                 → PAUSED
                 → CANCELED

PAUSED → QUEUED only after permitted resumption
```

Check cancellation between processing steps. Store checkpoints so a restart does not discard completed work or repeat every request.

### Standard error shape

```ts
interface ApiError {
  code:
    | "UNAUTHORIZED"
    | "FORBIDDEN"
    | "VALIDATION_FAILED"
    | "NOT_FOUND"
    | "UNSUPPORTED_QUERY"
    | "SOURCE_PAUSED"
    | "SOURCE_UNAVAILABLE"
    | "IMPORT_REJECTED"
    | "CONFLICT"
    | "INTERNAL_ERROR";

  message: string;
  requestId: string;
  fieldErrors?: Record<string, string[]>;
}
```

Return safe messages to users. Do not expose source documents, personal details, secrets, or stack traces in errors.

## 5. Build order and completion gates

### Stage one: Working search foundation

1. Create shared types and validation schemas.
2. Implement database migrations and repositories.
3. Add authentication and server-side authorization.
4. Implement manual case and observation entry.
5. Build bail and custody projections.
6. Implement saved-record search with explicit scope.
7. Build results and expandable evidence.
8. Add field-specific review.
9. Implement authorized CSV export.

**Gate:** a manually entered case can move through entry, evidence, review, search, and export without any live integration.

### Stage two: Import and processing

1. Add upload validation and temporary storage.
2. Implement CSV preview, mapping, and idempotent commit.
3. Add resource-limited PDF extraction.
4. Preserve extraction outcomes and provenance.
5. Add corrections, conflicts, and suppression.
6. Implement retention and temporary-file cleanup.

**Gate:** unsupported or unreadable files produce honest failure states, not fabricated results.

### Stage three: Discovery infrastructure

1. Implement the source registry.
2. Add the adapter contract.
3. Implement shared source limits and pause controls.
4. Add job checkpoints, cancellation, and partial results.
5. Add only approved, tested live adapters.

**Gate:** a source failure cannot turn into a completed zero-match search.

### Stage four: Validation and deployment

Test at minimum:

- Null and zero amounts.
- Inclusive/exclusive amount boundaries.
- Provisional versus reviewed operative bail.
- Superseded and conflicting orders.
- Unknown, old, released, transferred, and conflicting custody.
- Same-name different people.
- Duplicate imports and related dockets.
- Wrong, unreadable, and oversized documents.
- Unauthorized detail, evidence, and export access.
- Spreadsheet formula handling.
- Rate-limit pause across simultaneous jobs.
- Cancellation and process restart.
- Export snapshot consistency.
- Suppression and retention behavior.
- Synthetic/real-data separation.

**Gate:** real records are used only after private deployment, authorization, retention, and logging behavior have been checked.

The essential separation is now explicit:

```text
DISCOVERY finds candidates.
EXTRACTION records observations.
REVIEW evaluates specific evidence.
PROJECTIONS express the supported interpretation.
SEARCH filters that interpretation.
EXPORT preserves the same scope.
```

Approve or adjust this scaffold: it keeps the search page simple while preventing the engine underneath from confusing discovery, evidence, and certainty.
