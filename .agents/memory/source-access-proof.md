---
name: Source proof is client-specific
description: Calendar and PDF access must be proven using the same request methods used by the live adapter.
---

Treat a source-access proof as specific to the HTTP/browser methods actually tested. Calendar access alone does not establish docket access, and a successful standard HTTP PDF download does not prove Playwright's request client will work.

**Why:** On October 6, 2026, ordinary browser calendar submission and a standard HTTP docket download succeeded during assessment. The integrated browser-calendar job later received HTTP 403 for its Playwright-client PDF request. The cause of the denial was not established.

**How to apply:** Demonstrate both retrieval stages using the actual integrated methods before calling live search complete. After denial, preserve the source-wide pause and request history. Disclose and obtain approval for a changed method; do not infer authorization or a network cause from a previously successful client.

A bounded download assessment is not approval to resume broader collection, even if the assessment succeeds.

**Why:** The user approved one standard-HTTP check after an integrated-client denial. That check succeeded while the source-wide pause remained intact; its approval covered one request only.

**How to apply:** Count the approved check against the original job budget and retain its evidence. Obtain separate approval before enabling a changed collection method or making additional source requests. Do not reuse a single-request approval.

An empty development request ledger does not erase the earlier unresolved denial or supply fresh access proof.

**Why:** During safeguard preparation, the development source row had null verification/approval fields and no recorded requests, despite the previously observed integrated-client denial.

**How to apply:** Keep collection disabled when proof is missing. Do not seed successful proof or reuse the consumed one-request approval to make the search interface usable; obtain a newly scoped exact-client assessment.

The exact browser asset policy and calendar-form validation are part of method-specific access proof, not incidental implementation details.

**Why:** A prior browser workflow had working calendar results while the next integrated client returned only the search form; the failing run retained no blocked-asset paths or DOM snapshot, so the cause could not be established. A later offline audit found stricter handling of versioned bundle URLs but cannot prove that this caused the live result.

**How to apply:** Require fresh approval and verification whenever the browser asset allowlist, form-submission checks, or HTTP client changes. Treat a successful HTTP status, a visible form, or a plausible code-level cause as insufficient proof of a submitted, validated calendar query.

Console-error counts alone do not prove a required-script or form failure.

**Why:** A bounded run loaded both known bundles successfully but stopped before submission on two console errors. Offline browser fixtures then demonstrated that intentionally blocked optional images also emit console errors; the live cause remained unresolved because only counts were retained.

**How to apply:** Classify optional-resource noise only with exact provenance and a demonstrated browser signature. Keep unclassified errors fail-closed, never retrospectively reclassify a historical run from counts alone, and never record raw console text or token-bearing URLs.

Use fixed public control labels and reason categories for form validation failures, not a single generic mismatch code.

**Why:** Once bundle loading and optional aborts were distinguished, a live run stopped on a control mismatch; no retained evidence identified which field was missing, disabled, unassociated or changed. That prevented offline diagnosis despite a correctly stopped request stream.

**How to apply:** Keep private values and hidden tokens out of logs. Retain only bounded public labels and boolean/state reasons; do not reinterpret missing historical diagnostics as proof that a specific control caused the failure.

Keep cross-language public diagnostic contracts in sync and test the actual wire-message envelope against the worker's literal labels.

**Why:** A later authorized calendar-only attempt stopped before Search when the parent rejected a public diagnostic from the worker's newer control/reason set. The exact form failure was lost, so the protocol error did not establish which source control failed.

**How to apply:** Add parity checks when either side introduces diagnostic labels. Correcting reporting offline does not validate the source form or authorize another live attempt.

Distinguish public UI widgets from their native submitted model controls; do not assume every dropdown has its own submission name.

**Why:** A live preflight identified unnamed public widgets. A later hidden-model/layout assumption also failed without identifying their actual native submission model. The source backing-field layout was not retained.

**How to apply:** Require unambiguous source-DOM association and matching actual native submission data before accepting a backing control. Never infer a server field name, waive readback, or treat a hypothetical public form fixture as source proof. Collect all bounded public-control failures in one pass. When a guessed backing layout fails, stop repeating PDF pilots and obtain separately authorized source-backed public form/submission evidence first.

Use the exact source event label, not grammatical variants inferred from a
user-facing method name.

**Why:** The October 12, 2026 approved public-form inventory found singular
“Preliminary Arraignment” under the Allegheny Common Pleas criminal office, but
not plural “Preliminary Arraignments.” This observation established a public
option, not submitted search/PDF proof or MDJ coverage.

**How to apply:** Preserve the user's chosen method while distinguishing its
display name from the exact observed portal event. Disclose the precise label
in later verification scopes; never silently substitute events or treat a
recognized public option as permission to submit a search.

If a filing-mode inspection leaves court selection unestablished, investigate
the recognizer's blind spots before another Search/PDF pilot.

**Why:** An approved public-form observation could select filing mode but did
not identify a Court Type widget; recognized court-related widgets were
inactive and other selects were unclassified. It did not establish the actual
court-context label, control type, ownership or dependency sequence.

**How to apply:** Do not infer unsupported MDJ coverage, an empty search or a
network cause from this state. Prepare source-backed public-control evidence
without assuming a particular Court Type select label or native-form ownership
boundary. Native submission still requires validated form ownership and
bindings; a completed diagnostic protocol is not successful court coverage.

Broader observational inventory is not permission to interact with newly
discovered controls or infer their role from a recognized option.

**Why:** The failed select-only recognizer could not reveal controls outside the
search form or non-select widgets. Expanding observation addresses that blind
spot, but an MDJ-labeled option alone does not establish the controlling court
context or its dependency sequence.

**How to apply:** Separate evidence collection from adapter actions. Observe
bounded public-label/widget/ownership categories before and after the already
established filing-mode change; do not click or select unknown court controls.
Keep unknown text and private identities redacted, historical diagnostics
readable, and require fresh method-specific approval for any later source
observation. Broader observation never relaxes native submitted-binding checks.

Inventory-limit failures need distinct closed guard reasons even before any
inventory metadata can be retained.

**Why:** A separately approved source observation completed its allowed GETs
but stopped before the first inventory snapshot with a generic invalid-control
code. Network success and local fixture success could not identify which
inventory guard rejected the real page.

**How to apply:** Keep existing bounds and redaction intact; distinguish widget,
form-element, option and ARIA/group-reference limit categories without retaining
raw text or private identities. Do not retrospectively assign a category to
the generic historical failure, raise limits or reuse its consumed approval.
Generic calendar exception-path status/visibility markers are not source-DOM
observations or proof that a filing diagnostic attempted Search.

For observational inventory only, oversized option lists can remain explicitly
uninspected while other bounded controls are observed; unknown is not zero.

**Why:** A source-backed guard inspection established that at least one dropdown
exceeded the option-observation limit, causing the broad inventory to retain no
control metadata. The offending widget's identity/purpose was not established.

**How to apply:** Keep the existing option limit; do not read or truncate
oversized choices. Mark their counts and recognized/selected choices unknown,
retain only otherwise permitted public control-state metadata, and observe
in-bounds controls separately. This is partial diagnostic evidence, never
coverage, absence or submission proof. Required adapter bindings/scope must
still fail closed until actually established. Changed diagnostic metadata and
partial-observation behavior need a new method and fresh source approval.

Search activation** after filing mode, with no other selections, Search, dates

**Why:** The user selected “Allow Advanced Search activation.”

**How to apply:** Use a fresh current-method permit, keep the same three-GET

The user extended continued inspections to allow local **Allegheny County

**Why:** The user selected “Allow local Allegheny selection,” with no additional

**How to apply:** Keep fresh current-method permits and the unchanged three

select's single enabled exact Allegheny choice, when visible/enabled and owned

The user also approved read-only **public court-office label and displayed-code
identification**, with no additional comments.

**Why:** The user selected “Allow public office identification.”

**How to apply:** Retain only bounded, recognized institutional labels and
displayed public office codes, after the approved filing/Advanced Search/Allegheny
sequence. Exclude private option values, names and identities. Preserve the same
three paced GETs, fresh permits and all stops; no office selection, Search, dates,
PDFs or dependent transmissions. Plain numeric district codes must remain
court-type-unverified; they are not MDJ-context or submitted-binding proof.
An empty recognized-code list leaves source choices unresolved, not absent.
After bounded recognition approaches fail, request a redacted public example
rather than silently inspecting underlying option values or guessing an office.

Filing mode followed by **Advanced Search** activates the source's **County**
control; local Allegheny selection activates a court-office-related dropdown.

**Why:** Source-backed read-only inventories observed one search-form-owned,

The later dependency sequence and MDJ context remain unproven.

**How to apply:** Recognize the exact source-listed Advanced Search label, not a
guessed identity or generic word match. Its eligibility is not proof of its
native submission bindings. Advanced Search activation is now approved within
the scope above; keep dependent traffic blocked. Local Allegheny selection is
now separately approved under the limits above. Do not treat the available Allegheny choice, an
unclassified court-office-related dropdown, its option count or hidden Criminal choice as MDJ coverage,
an absence proof, a submitted binding or permission to choose Common Pleas.
